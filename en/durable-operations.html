Durable operations

Tasks that span minutes, hours, or restarts inherit familiar distributed-systems problems: consistency, replay, idempotency, and coordination.

Operational memory

Working state does not have to be only conversation

Long trajectories become more robust when progress exists in explicit artifacts: todo lists, feature status, notes, test results, commits, plans, and output manifests.

Inspectable

Humans and future sessions can understand the current point.

Versionable

Changes in plan and state can be compared and reverted.

Recoverable

A new process can resume without the previous instance’s memory.

Why long-running work changes the problem

A five-second call can often be retried with little coordination. A task that lasts hours can encounter worker failure, disconnects, sandbox reclamation, delayed approval, and process replacement.

A durable log does not make external effects atomicIt helps remember what was requested and observed, but it cannot guarantee that an external API did not commit before the crash.

Control state and world state can diverge

Imagine create_ticket(...). The remote system creates the ticket; the connection drops before the response arrives. The harness knows it asked, but not whether the action committed. Blind replay can create a duplicate.

Retry policy must be tool-specific

An operation is idempotent when repeating the same intended operation has the same intended effect as performing it once.

f(f(s)) = f(s)

OperationRisk if repeatedProtection
set_ticket_status(id, "closed")Usually low if “closed” is already the final state.Idempotent semantics.
create_order(...)Duplicate order.Idempotency key and uniqueness.
send_email(...)Message sent twice.Operation ID and deduplication.
charge_card(...)Duplicate charge.Idempotency key plus provider reconciliation.
  1. Before the action: generate and persist a unique operation ID.
  2. Inside the tool: accept the ID and reject duplicates or return the original result.
  3. After timeout: query state by ID before retrying.
  4. When certainty is impossible: escalate rather than convert ambiguity into a new consequence.

Concurrency creates shared-state consistency problems

Multiple workers or subagents can improve throughput, but raise questions about commit order, conflicts, ownership, and the authoritative event stream.

Useful strategies

  • serialize writes
  • partition by resource
  • explicit ownership
  • independent commits
  • controlled merge

Risk signals

  • two agents in the same area
  • requirements changing in parallel
  • unversioned state
  • external effects without IDs
  • no integration owner

Subagents are a harness choice

Delegation helps when work is genuinely independent and results can be integrated cheaply. In sequential work, communication can cost more than execution.

Delegate whenAvoid when
subtasks have clear boundaries and deliverableseach step depends heavily on the previous one
sources or modules are independenteveryone needs the same large context
the merge can be checked objectivelyworkers write to the same state
latency matters more than total costcoordination cost dominates
Delegation should be justified by task decomposition, not by the belief that more agents are inherently better.

Agent legibility

Agent-legible environments make important information discoverable through mechanisms the agent can inspect. They replace tribal knowledge with artifacts.

  • Structured documentation points to sources of truth.
  • Packages and ownership have predictable boundaries.
  • Build, test, and launch commands are clear.
  • Logs, metrics, and screenshots are queryable.
  • Mechanical rules become linters and structural tests.
  • The current application state is reproducible.
Mechanism beats memoryIf a rule is mechanically decidable, encode it in a schema, test, lint rule, or boundary. The model need not remember perfectly what the system can reject automatically.

Check your understanding

Does an event log make every tool call safe to replay?

No. It preserves intent and observations, but the external effect may already have committed. Replay safety depends on operation semantics.

When does a subagent improve the system?

When there is independent decomposition, cheap integration, and explicit coordination. It can hurt sequential trajectories.

What is agent legibility?

Making assumptions, state, documentation, tests, and telemetry discoverable through interfaces the agent can use.
