Verification and evaluation

“Done” is a claim. A reliable system looks for external evidence, measures consistency, and separates producing from judging.

Ground truth

Self-reported completion is not proof

“The bug is fixed” is a language output. Stronger evidence would reproduce the original failure, run regressions, exercise the flow end to end, and inspect the affected state.

Practical ruleWhenever possible, tie completion to observable state outside the model’s own assertion.

Use mechanisms for mechanically decidable rules

Some decisions genuinely require interpretation; others can be checked reliably by code.

Judgment

Model or human

  • Is this result relevant?
  • Does the explanation satisfy the intent?
  • Is the design coherent?
  • Which file should be investigated?
Enforcement

Deterministic validator

  • Is the JSON valid?
  • Did the path escape the mount?
  • Was the budget exceeded?
  • Did a forbidden dependency appear?
The model should not have to remember a rule that the system can enforce cheaply and objectively.

Generating and evaluating are different roles

Prose, research, planning, and design do not have a single deterministic test. Separating generation from critique can expose omissions and inconsistencies.

External feedback closes the loop

A tool that changes state but cannot expose the result creates a weak feedback loop. Harness engineering must make ground truth queryable.

Code

Compiler, tests, lint, coverage, diff, and local execution.

Product

Screenshots, DOM, navigation, accessibility, and visual state.

Operations

Logs, metrics, traces, database, APIs, and provisioned resources.

  1. Act: make a bounded change.
  2. Observe: obtain the relevant consequence and telemetry.
  3. Compare: check against the success criterion.
  4. Revise: correct the strategy and repeat within limits.

The first set helps people debug the harness. The second gives the model evidence to debug the system it is working on.

An agent harness operates; an evaluation harness measures

An evaluation harness provisions stable environments, runs tasks end to end, records trials, invokes graders, and aggregates results. It measures more than the model.

measured performance = F(model, harness, environment, task, grader)

What to measure

  • Success rate and consistency across repeated trials.
  • Correct final state, not merely a plausible transcript.
  • Failure categories: selection, contract, context, environment, recovery.
  • Tokens, cost, latency, tool calls, and human intervention.
  • Adverse effects: duplicate side effects, policy violations, and regressions.

Infrastructure can change benchmark scores

Agentic coding benchmarks depend on installation, compilation, CPU, memory, disk, network, and processes. Too few resources create infrastructure failures; abundant resources may enable different strategies. Meaningful score comparison requires documented conditions.

Treat small differences cautiouslyIf resources, timeout, tooling, and environment are not equivalent, a leaderboard may be measuring infrastructure as much as agent behavior.

Every harness component is a hypothesis

Scaffolding is created to compensate for observed limitations. When the model changes, some of it can become unnecessary, expensive, or harmful. Measure quality and cost component by component.

A harness improvement should justify both its quality lift and execution cost for the current model and task distribution.

Check your understanding

Why is a deterministic test often stronger than a model grader?

Decidable properties can be checked reproducibly, without another model’s interpretive variability.

Does an evaluation measure only the model?

No. It measures the interaction among model, harness, environment, task, and grader.

Why reevaluate the harness when the model changes?

Old workarounds may lose their benefit, retain their cost, and create new failure modes.
