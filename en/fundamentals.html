From model to agent

Key idea

A model call is not yet an agent

An inference can be represented abstractly as an output y sampled from the model distribution conditioned on context c. That describes generation—not execution.

y ~ pθ( · | c )

Nothing in this expression guarantees that a command runs, a file changes, an error is observed, or work continues after the first response. That requires an external process that interprets the output, applies rules, executes actions, and decides what happens next.

The important boundary is not “chatbot versus agent” as a marketing label. It is whether model output participates in a controlled interaction loop with external state.

The minimal agent loop

The handbook proposes four evolving objects. The harness selects context from state, calls the model, executes an action when requested, and incorporates the resulting observation into the next state.

st → ct = G(st) → at = M(ct) → ot = E(at) → st+1 = U(st, at, ot)

What each function does

G · selection

Active context

Chooses, from available state, what the model needs to see now.

M · inference

Model decision

Produces final text or a structured action request.

E · execution

Environment

Applies the action to the world and produces a verifiable observation.

U · update

State

Records results, progress, failures, and what the next step will need.

Five components that are not synonyms

Separating the objects helps localize failures. A model error, routing error, and sandbox error can all produce the same superficial symptom—“the task failed”—but require different fixes.

ComponentFunctionDiagnostic question
ModelThe learned inference system.Did it interpret and decide well?
HarnessDrives the loop and connects inference to actions.Did the model receive and have access to what it needed?
SessionA logical container for history and state.What survives turns and restarts?
ToolA callable capability exposed to the model.Are the contract and result usable?
SandboxA controlled execution environment.What can code reach and modify?
Control and execution are different planesThe harness decides what should happen; the sandbox constrains where and how it happens. They can share a process in a prototype, but they should not share trust assumptions.

What the harness actually controls

Not every system implements all of this in one component. Yet these decisions must exist somewhere:

Before inference

  • instructions and context
  • visible tools
  • retrieved state
  • remaining budget

During action

  • contract validation
  • permission and approval
  • routing
  • isolated execution

After action

  • result representation
  • persistence and compaction
  • retry and recovery
  • verification and stopping

Agent or workflow?

In a workflow, the execution path is largely determined by application code. In an agent, the model dynamically chooses strategies and actions. Real systems often combine both.

Check your understanding

Why is a system prompt not the entire harness?

Instructions are only one input. A harness can also control tools, state, approvals, execution, errors, budgets, recovery, and verification.

What turns model output into action?

An external process interprets the request, validates policy, calls a tool in the environment, and returns the observation to the loop.

Why separate session from context?

A session can retain more history than the next inference can or should see, while active context may also contain ephemeral material that was never persisted.
