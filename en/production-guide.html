Integrated view

The complete mental model

A task enters a system with persistent state. The harness selects context, drives the model, controls tools, and interprets observations. Hard boundaries surround execution; feedback and verification close the loop.

Failure taxonomy

Classification changes the response. “The agent failed” is too broad to guide engineering.

Tool selection

The capability exists, but the model chooses the wrong operation.

Contract

The operation is correct, but arguments or preconditions are invalid.

Observation

The action succeeds, but the result is noisy, ambiguous, or incomplete.

Context

Important information is missing, stale, or lost during compaction.

State

Progress, approvals, plans, or prior actions are lost.

Environment

Packages, files, resources, or permissions differ from assumptions.

Verification

The model declares success without checking external state.

Authorization

The agent is overblocked or receives excessive power.

Recovery

A retry duplicates an effect or restart cannot reconcile the world.

Coordination

Subagents duplicate work, diverge, or compete over state.

Budget

Turns, time, cost, or concurrency run out before success.

Provenance

Untrusted content gains authority and redirects the agent.

Skill

A relevant skill induces incorrect implementation or an efficiency regression.

Plausible misconceptions

MisconceptionCorrection
“The harness is the system prompt.”Instructions are one part; the loop, tools, state, recovery, and verification matter too.
“The harness is the sandbox.”The harness controls work; a sandbox is one environment where work executes.
“MCP is the agent.”MCP standardizes capability surfaces; it does not define the complete orchestration.
“Context window equals memory.”Durable state can exist outside the current context.
“Compaction preserves everything.”A summary is a lossy representation.
“More tools always improve capability.”Overlap increases ambiguity and selection burden.
“Approval makes arbitrary execution safe.”Approval controls decisions; containment controls reach.
“If a tool failed, retry it.”Non-idempotent effects can duplicate consequences.
“The agent said it finished.”Self-report is weaker than external evidence.
“More agents are better.”Coordination can dominate sequential tasks.
“A better model keeps all old scaffolding useful.”Harness hypotheses expire; run ablations.
“Skills are harmless prompt templates.”They can contain instructions, resources, and scripts; treat them as provenance-bearing code/configuration.

15 questions before production

  1. What does the model receive? Instructions, history, tools, summaries, and artifacts.
  2. Who controls the loop? Application, managed harness, workflow, or another agent.
  3. Which actions exist? Functions, MCP, shell, browser, APIs, files, and subagents.
  4. Where do they execute? Trusted process, local machine, container, VM, or remote service.
  5. What survives? Events, files, snapshots, and effects after a crash or new turn.
  6. Which rules are mechanical? Schemas, mounts, network, approvals, tests, and budgets.
  7. How are errors represented? Exception, retry, model-visible observation, or escalation.
  8. What is safe to repeat? Idempotent operations, deduplicated operations, or neither.
  9. Where is ground truth? Tests, logs, UI, database, APIs, and external responses.
  10. What proves completion? Claim, validator, external state, evaluator, or person.
  11. How does the loop stop? Turns, time, tokens, cost, policy, and success.
  12. How does it resume? Resume, retry, reprovision, rollback, or restart.
  13. Which data is untrusted? Web, files, memory, tools, skills, and subagents.
  14. How do subagents coordinate? Ownership, shared state, merge policy, and limits.
  15. How is the harness evaluated? Ablations, representative tasks, stable environments, and outcomes.

A pragmatic implementation order

The summary in nine sentences

  • The model supplies learned capability.
  • The harness connects that capability to work.
  • The session determines what can survive.
  • Context policy determines what the model sees now.
  • The environment determines what can actually happen.
  • Permissions and containment determine how far failure can reach.
  • Feedback shows what happened.
  • Verification turns “done” into evidence.
  • Evaluation shows whether the harness helps or only adds machinery.
